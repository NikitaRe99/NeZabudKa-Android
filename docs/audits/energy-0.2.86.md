# Энергоэффективность НеЗабудьКа 0.2.86

Проверка: 23 октября 2026 года, исходный код `67c3015`, Samsung S9 SM-G960U1, Android 10. Изменения в приложение по результатам проверки не вносились.

## Вывод

Признаков постоянной тяжёлой работы в фоне при проверке не обнаружено. Основной резерв — работа во время диктовки: повторное чтение аудио, промежуточное распознавание и загрузка моделей. Для фоновой работы полезнее всего сократить лишние обновления виджетов и обращения к сети. Размер возможной экономии пока не измерен.

## Что измерено

Приложение было свёрнуто на домашний экран; процесс оставался тем же. По `/proc/PID/stat`, при частоте счётчика 100 Гц:

| Проверка | Длительность | Процессорное время приложения |
| --- | ---: | ---: |
| Первый интервал, включая переход в фон | 31,75 с | 0,36 с |
| Повторный спокойный интервал | 211,95 с | 0,14 с |

Второй результат соответствует примерно 0,07% одного процессорного ядра за этот интервал. В отдельном снимке фоновых сервисов приложения не было, системный список удерживаемых wake lock был пуст. Память процесса без активной диктовки — около 57 МиБ PSS; это не оценка памяти с загруженными речевыми моделями.

Ограничения: телефон подключён по USB, экран оставался включённым, распознавание не запускалось. Это проверка спокойного фона, а не замер разряда батареи или ночного сна. Историческая статистика Android смешивает предыдущие версии, загрузки обновлений и проверки, поэтому использовать её как результат для 0.2.86 нельзя. Исходные снимки сохранены локально в `build/energy-audit/`.

## Что улучшить

### 1. Не перечитывать всю запись при каждом промежуточном распознавании

**Приоритет: высокий для диктовки.**

`WavAudio.kt:145`, `AssistantViewModel.kt:788`, `Gigaam.kt:125`.

Во время предпросмотра GigaAM запись периодически целиком читается из WAV и преобразуется в новый `FloatArray`. Чем дольше диктовка, тем больше повторных чтений и выделений памяти. Завершённые фрагменты распознавания уже кешируются, но получение аудиоданных всё ещё повторяет работу. После остановки выполняется полный итоговый проход.

Предлагается хранить PCM в буфере и передавать только добавившийся звук, сохраняя необходимое перекрытие между фрагментами. При длительной тишине можно пропускать промежуточное распознавание; при нагреве — увеличивать его интервал. Итоговый проход сначала оставить для качества. Повторное использование его результатов допустимо только после проверки границ фрагментов и точности текста.

Проверка: одинаковые записи на 30 секунд и 5 минут, предпросмотр включён и выключен; сравнить CPU, выделения памяти, задержку и итоговый текст.

### 2. Сократить повторную загрузку моделей

**Приоритет: высокий при нескольких диктовках подряд.**

`NotePunctuation.kt:29–46`, `Gigaam.kt:96`.

RUPunct заново читает словарь и конфигурацию, создаёт токенизатор и ONNX-сессию для каждого текста. У GigaAM повторная загрузка зависит от настройки удержания модели. Whisper уже имеет механизм освобождения после простоя — его не нужно дублировать.

Предлагается кешировать неизменяемые словарь и конфигурацию, а сессию пунктуации ненадолго сохранять между запросами, например на 30–60 секунд, пока приложение открыто. При уходе в фон и нехватке памяти освобождать. Нужна синхронизация доступа и безопасная смена модели. Это обмен дополнительной памяти на меньшую работу при следующем запросе; само наличие модели в памяти не означает постоянный расход CPU.

Проверка: серия из десяти коротких запросов с холодной и сохранённой сессией; сравнить время, CPU и пиковую память.

### 3. Убрать лишние обновления виджетов

**Приоритет: средний, только при установленных виджетах.**

`notes_widget_info.xml:4`, `reminders_widget_info.xml:4`, `HomeWidgets.kt:59–113`.

Оба провайдера запрашивают обновление каждые 30 минут. При этом уже есть обновления по изменениям базы, настройкам, действиям пользователя и смене дня. Изменения базы обрабатываются сразу, без объединения серии событий. Каждый виджет повторяет запросы данных и получает полное обновление оболочки вместе с обновлением списка. Даже для отключённой функции данные запрашиваются до отображения заглушки.

Предлагается:

- Для заметок перейти на обновления по событиям, отключив периодический запрос.
- Для напоминаний сначала проверить восстановление актуальности после завершения процесса и при отсутствии разрешений; затем заменить частый резервный опрос более редким или обновлением на ближайшую значимую дату.
- Объединять близкие изменения базы в течение 200–500 мс, переиспользовать одинаковые результаты запросов и обновлять только изменившиеся части.
- Для заглушки отключённой функции не загружать содержимое списка.

Android разрешает отключить периодическое обновление значением `updatePeriodMillis=0`; полное обновление виджета является наиболее затратным видом обновления. [Документация Android](https://developer.android.com/develop/ui/views/appwidgets/advanced).

Проверка: создание, редактирование и удаление записей; полночь, перезагрузка, завершение процесса, несколько виджетов и отключение функции. Экономия не должна приводить к устаревшим данным.

### 4. Реже записывать полную резервную копию

**Приоритет: средний для большой базы и выбранной пользователем папки.**

`UserDataBackup.kt:51–140`, `UserModelsStorage.kt:237`.

После паузы в изменениях на 1,2 секунды механизм копирования повторно читает таблицы и записывает весь JSON. Запись включает проверочное чтение и ротацию предыдущей копии. Изменения состояния хранилища тоже могут инициировать работу, даже если переносимое содержимое не изменилось. Этот механизм используется при выбранной пользователем папке, а не у всех пользователей.

Предлагается сравнивать переносимый снимок с предыдущим и пропускать идентичные копии, переиспользовать согласованный снимок базы и объединять частые изменения. Увеличение задержки до 3–10 секунд потребует отдельного решения о допустимой потере последних изменений резервной копии при аварийном завершении. Атомарную запись, проверку и предыдущую копию сохранить.

### 5. Ограничить автоматические проверки обновлений

**Приоритет: средний при частом открытии приложения.**

`MainActivity.kt:553`, `GithubAppUpdater.kt:121,173–185`.

При запуске создаётся разовая задача проверки; ограничения по давности последней проверки нет. Для поиска версии загружаются все страницы истории релизов, даже когда новой версии нет.

Предлагается проверять автоматически не чаще одного раза в 6–12 часов, ручную проверку выполнять сразу. Использовать условные HTTP-запросы с ETag; дополнительные страницы истории получать только при найденном обновлении, когда нужны изменения пропущенных версий. Постоянные ошибки подписи или несовместимости не стоит повторять как временные сетевые сбои.

Для необязательной фоновой работы Android рекомендует подходящие ограничения по сети и батарее и объединение совместимых задач. Ручные действия пользователя не следует задерживать без необходимости. [Рекомендации Android](https://developer.android.com/develop/background-work/background-tasks/optimize-battery).

### 6. Подобрать число потоков по измерениям

**Приоритет: экспериментальный.**

`Gigaam.kt:89`, `ClassicNluClient.kt:302`, `NotePunctuation.kt:44`.

Автоматический выбор ориентирован преимущественно на скорость. Более быстрый режим не всегда экономичнее, но и уменьшение числа потоков само по себе не гарантирует экономию: вычисление может просто длиться дольше.

Сравнить 1, 2 и 4 потока на одинаковом аудио. Отдельно проверить ожидание рабочих потоков ONNX Runtime: активное ожидание может снижать задержку ценой CPU и энергии. [Документация ONNX Runtime](https://onnxruntime.ai/docs/performance/tune-performance/threading.html).

В проекте используется ONNX Runtime 1.28.0. В этой версии значение ожидания по умолчанию зависит от сборки библиотеки, поэтому сначала нужно проверить фактическую конфигурацию Android-артефакта, а не считать ожидание включённым. [Исходный код конфигурации 1.28.0](https://raw.githubusercontent.com/microsoft/onnxruntime/v1.28.0/include/onnxruntime/core/session/onnxruntime_session_options_config_keys.h).

## Что уже сделано разумно

- Микрофон работает по действию пользователя; постоянного прослушивания нет.
- Речевые модели освобождаются при уходе в фон или нехватке памяти.
- Нет постоянно работающего сервиса для ожидания команд.
- Обновление времени на экране напоминаний привязано к видимому экрану и изменению отображаемого времени.
- Циклы перетаскивания работают только во время жеста, а не в спокойном фоне.
- Точные будильники используются для напоминаний. При отключении функции сигналы отменяются.
- Суточное обновление виджетов использует неточный будильник без пробуждения устройства; без виджетов оно не нужно и отменяется.
- Очистка корзины выполняется периодической задачей, постоянного опроса нет.

Снижать точность напоминаний или убирать необходимые разрешения ради экономии не предлагается.

## Порядок дальнейшей работы

Сначала исправить повторное чтение аудио и загрузку RUPunct. Затем сократить работу виджетов, копирования и проверок обновлений. Настройку потоков выбирать после сравнительных измерений.

Для проверки автономности нужны повторяемые испытания без USB: одинаковый сценарий диктовки и отдельные 8–12 часов с выключенным экраном, с виджетами и без них. Сравнивать исходную и изменённую сборки на одном телефоне, с одинаковыми настройками, сетью и уровнем сигнала. До этого обещать конкретный процент экономии нельзя.
